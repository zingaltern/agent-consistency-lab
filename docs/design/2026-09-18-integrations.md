# 设计文档 C：外围集成——MCP 工具服务 + 可观测导出落地

* 版本：v1.0（2026-09-18）
* 目标读者：开发 Agent（自包含；先读 §0 再动代码）
* 状态：待评审
* 关联背景：项目当前的对外形态只有 CLI 与报告。真实模型路径（B-M1）已通，
  工具参数 schema 已补齐（PR #5/#7），因此「把治理层接到别人的 agent 上」这件事
  第一次变得便宜。与之并行的另一条路是把既有的 OTLP 导出（B-M4）落到一个真实后端上。

---

## 0. 第一性原理推导

1. **集成层不产生结论**。本项目的结论全部来自 `harness/` 的语义与 `opsenv/` 的测量方法学；
   集成层只改变两件事：**谁能调用这些工具**、**别人用什么工具看这些数据**。
   由此推出第一条纪律：**任何集成改动都不允许让"结论更强"的暗示出现**——
   接上 Grafana 不等于"生产可用"，能被 MCP 客户端调用不等于"平台"。
2. **内核零侵入是既有的、被验证过的模式**。`[eval]`（LangGraph 对照）与
   `[otel]`（OTLP 导出）已经证明：附加能力可以完全装进 extra，内核依赖仍然只有 pydantic，
   默认路径行为逐字不变。集成层照抄这条模式，不发明新机制。
3. **治理层要复用，不能重写**。工具执行不是"调用一个函数"：它是
   `harness/loop.py::_execute_tool` 的七步固定管线（日志权威 → 未注册工具 → 幂等/outbox 对账 →
   审批门 → TOCTOU 复核 → 意图行 → 执行与闭合）。任何绕过这条管线的"轻量执行器"
   都会产出第二套语义——那等于把项目最值钱的东西复制坏。因此集成层的第一技术问题
   是**如何复用这条管线**（见 §5 开放问题 1）。
4. **权威只有一个**。MCP 服务不能自己记状态、不能缓存审批结论、不能在内存里维护
   "当前 run"的权威副本：状态只能从事件日志折叠。客户端断开、服务被强杀，
   都不允许产生新的语义（这正是本项目要展示的东西）。
5. **本机的现实约束**：网络对部分域名不稳定、Docker 未必可用。因此可观测那一条
   必须是"可选路径"，不能成为任何验收门的前置条件。

## 1. 目标 / 非目标

### 目标

* **G1｜治理型 MCP 工具服务（stdio，本地单用户）**：把工具注册表暴露为 MCP 工具；
  每次调用走 `_execute_tool` 的既有管线——审批门、幂等键、outbox、ArgPolicy、预算账本全部生效。
* **G2｜审批在 MCP 形态下可用且可移植**：默认形态是"待审批作为工具结果返回"，
  **不依赖 elicitation**（客户端支持程度不一）；另提供显式的
  `list_pending_approvals` / `approve`（含 reject / edit）工具对作为主路径。
* **G3｜崩溃语义在集成形态下依然成立、且可演示**：强杀 MCP 服务进程 → 重启 →
  同一 run 继续 → **外部账本证明副作用恰好一次**（不重跑）。
* **G4｜可观测导出落到真实后端（可选路径）**：`harness.trace --otlp-endpoint` 已有，
  本包补的是"一条命令起后端 + 导入 + 看什么"的可复现路径与口径说明。
* **G5｜目录与依赖边界可审计**：集成代码在独立目录、独立 extra、独立测试标记；
  内核依赖不变、`verify` 作业时长不显著增长、既有 345 用例与 14 条门禁全绿。

### 非目标

* **不做多租户、鉴权、远程监听、守护进程、外部化存储**。MCP 服务必须是 **stdio 本地进程**；
  出现"服务化/平台/生产级"口径即越界（见 §8）。
* **不做实时流式**：MCP 是请求-响应；"边跑边看"不在本包内（可观测那条是事后导入）。
* **不新增权威状态**：不设独立的会话数据库、不缓存审批结论、不在服务端维护运行态副本。
* **不重写工具执行**：禁止另起一套"轻量执行器"绕过七步管线。
* **不改语义承诺**：`docs/semantics.md` 不因本包放宽或扩大任何一条。
* **不把 Docker/Jaeger 变成 CI 依赖**：可观测路径只在本地人工验证，CI 不进。

## 2. 需求列表

### R-C1｜MCP 工具服务（对应 G1）

* 传输：stdio；一个进程对应一个 run 目录（`--run-dir`），run 必须已存在或由本服务创建。
* `tools/list`：由 `ToolRegistry` 直接映射——`Tool.parameters`（JSON Schema）即 MCP 的
  `inputSchema`（PR #5 已补齐 `fakeworld` 四个工具与 `read_artifact`；本包需要为**新增工具**
  继续声明 schema，未声明的工具不得下发）。
* `tools/call`：**必须**走既有执行管线。允许的实现路径见 §5 开放问题 1 的裁决；
  无论哪条，都必须保留：审批门、幂等键（含 branch 维度）、outbox 三态、ArgPolicy 复核、
  TOCTOU 参数复核、事件日志 append-only。
* 失败语义可读：未注册工具、被策略拒绝、工具异常，各自给出可读错误
  （照 `_handle_tool_failure` 的分类：非幂等写异常 → `unknown` 等对账；只读/幂等 → `failed`）。
* **参数不合 schema 不构成失败语义**（2026-09-18 口径更正，来源：独立验证报告 P2-2）：
  执行前唯一的闸门是 ArgPolicy 与工具自身。下发 schema 与模型侧同源，是**自述**而不是第二道闸——
  在它与执行之间再插一个校验器必然与管线分叉（同一参数在两处得到不同判决）。
  ⇒ `query_metrics(service=12345)` 这类"不合 schema"的入参会被原样执行；
  它的结论由工具自身决定，不由 schema 决定。本条更正上面那句列举里的"参数不合 schema"。
  实现口径写在 `docs/integrations.md` §6.2。
* **顶层 `isError` 反映内层执行失败**（2026-09-18 行为更正，来源：独立验证报告 P2-3）：
  `approve` 的顶层 `status=approved` 说的是**决定**，`executed[]` 说的是**执行**。
  当 `executed[]` 含 `failed`/`unknown`/`rejected` 时顶层 `isError` 也置真，并附一句可读
  `note`。被堵死的只有"顶层 `isError` 恒假地宣称成功"这一种读法；
  `status` 的取值与其余语义不变（正对照：执行成功时 `isError` 仍为假）。

### R-C2｜审批（对应 G2）

* 写操作（`requires_approval=True`）的调用必须停在审批门，返回**可读的待审批结果**
  （含 `tool_call_id`、参数摘要、参数哈希、过期时间），不阻塞进程、不静默执行。
* 提供工具对：`list_pending_approvals(run_dir)`、`approve(tool_call_id, decision, ...)`，
  其中 decision 支持 approve / reject / **edit（改参）**——改参必须沿用既有的
  "改参 = 新调用 + 新幂等键 + 新批准"语义（`Loop.approve()` 已有实现，不得另写一套）。
* elicitation 只作为**可选增强**：探测到客户端不支持时必须自动退回默认形态，
  且该退回路径要有测试。

### R-C3｜崩溃与恢复演示（对应 G3）

* 提供一条可复现路径：MCP 服务在工具执行中途被 SIGKILL → 重启服务 → 对同一 run 继续 →
  **外部账本**（`world.db`，连 `-wal` 一起快照）显示副作用 1 次。
* 演示脚本或文档必须同时给出**对照组**（关掉 outbox / 下游不幂等时的重复），
  否则不算演示——只有对照才能说明"是谁在起作用"。
* 不得引入模拟：必须是真 SIGKILL 子进程（照 `experiments/` 的既有做法）。

### R-C4｜可观测导出落地（对应 G4）

* 产出：一份"怎么起后端、怎么导入、**看什么／不要看什么**"的说明 + 一条可复现命令。
  必须写明的三条口径（来自 `harness/trace.py`/`otel.py` 既有实现）：
  1. **时长是推导值**（`harness.duration_is_derived=true`），工具 span 是真实墙钟窗口，
     模型 span 是事件间隔推导——**不得用来讲性能**；
  2. **事后导入**，不是实时流；
  3. **trace 里没有账本**：审批、outbox、"发生了几次"都在事件日志与 `world.db` 里。
* 后端选型由所有者决定（Docker/Jaeger、Grafana Cloud、或本地 JSON 渲染）；
  文档要给出至少两条路径及其前置条件（本机网络对部分域名不稳定，Docker 未必可用）。

### R-C5｜目录、依赖与测试边界（对应 G5）

* 见 §3。**这是本包最容易被做坏的地方**：集成代码一旦渗进内核目录或默认依赖，
  项目的"零依赖内核"这条卖点就没了。

### R-C6｜数字与 claim

* 新增的对外数字（工具数、集成用例数、演示耗时等）一律登记为 claim
  （`reports/documented-facts.json`），引用处用锚点。

## 3. 接口与布局（**文件管理**：本包的重点之一）

### 3.1 放哪里：同仓库的独立目录，不进内核

**结论：放在同一个仓库的 `integrations/` 目录，用独立 extra 与独立测试标记隔离。**

理由（三条，按重要性）：

1. **它必须复用内核内部件**（七步执行管线、审批、账本）。放到独立仓库，
   要么把这些内部件升格为"对外 API"（过早冻结、锁死后续重构），要么复制一份（语义分叉）。
   两者都比"同仓库 + 明确边界"更差。
2. **它是外围，但不是垃圾**：与 MCP 客户端、OTLP 后端的兼容性会随外部生态变，
   需要跟内核一起被测试、被 CI 看住，而不是散落在本地。
3. **既有先例已经给出了边界写法**：`[eval]`、`[otel]` 都是同仓库、独立 extra、
   延迟 import、默认路径零改变。集成层照抄即可，不需要发明新机制。

### 3.2 目录布局

```
integrations/                 # 外围集成（可选装、可选跑）
  __init__.py
  mcp_server.py               # R-C1/R-C2：MCP 工具服务（stdio）
  observability.md            # R-C4：怎么起后端、怎么导入、看什么
docs/integrations.md          # 使用说明 + 边界（给人类读者）
tests/test_integrations_*.py  # 用例（分标记，见 3.4）
```

* `harness/`、`opsenv/`、`fakeworld/`、`experiments/` **一律不得** import `integrations/`
  （依赖方向单向：integrations → 内核）。这条要有测试守住（照 `test_otel.py` 里
  "顶层不含 otel import" 的做法）。
* 反向也要守：`import harness.*` 不得触发 MCP 的任何 import（延迟 import）。

### 3.3 依赖

* `pyproject.toml` 新增 `[project.optional-dependencies] mcp = [...]`；
  `dev` extra **不**包含它（避免"装了个 dev 就把 MCP 全家桶拉进来"）。
* 内核依赖仍然只有 `pydantic`——本包不得新增任何内核依赖。

### 3.4 测试与 CI

* 分两类：
  * **无外部依赖的用例**（工具映射、审批状态机、schema 校验、退回路径）→ 归入默认
    `pytest`，但总量必须小（目标是**给 verify 作业增加 ≤ 5 秒**）；
  * **需要真实 MCP 客户端/后端的用例** → 打新 marker（如 `mcp`），默认 addopts 过滤掉，
    只在显式调用时跑（照 `live` marker 的先例）。
* **不加新的 CI 作业**；`verify` 时长若增长超过 5 秒，必须在 PR 里说明并给出取舍。
* 既有门禁的语义与阈值一律不动。

### 3.5 文档归属

* `docs/integrations.md` 顶部必须写明：**这是外围集成，不改变任何结论的适用范围**；
  本仓库仍是实验台，不承诺生产可用。
* README 增加一小节（3–5 行）指向它，措辞不得使用"平台/服务化"。

## 5. 开放问题（开发代理先答再动手）

1. **【最要紧】如何在 MCP 形态下复用七步执行管线？**
   两条候选路线：
   * (a) 让 `Loop` 支持"外部驱动的工具执行"（无模型模式）——问题是给 loop 引入分叉；
   * (b) **把 `_execute_tool` 的七步抽成可复用单元**（例如
     `harness/execution.py::ToolExecutor`），loop 与 MCP 服务共用同一实现。
   **倾向 (b)**：管线本身已经是一条固定顺序的函数，抽出后语义天然一致，
   loop 的改动是"把内联调用换成委托"，属于可测的机械改动；
   (a) 会让 loop 承担两种驱动模式，测试面翻倍。
   裁决需给出：抽取边界、既有 345 用例的受影响面、以及"两处调用点行为一致"的证明方式。
2. **一次 MCP 会话与 run 的映射**：会话是最小生命周期还是 run 是最小生命周期？
   倾向：**run 是权威，会话只是句柄**（客户端可断可续；状态从事件日志折叠）。
3. **预算与成本归属**：外部 agent 驱动时，`--budget-usd` 按 run 还是按会话？
   倾向按 run（与既有语义一致），会话不做二次记账。
4. **崩溃演示的判定口径**：杀谁、怎么证明（沿用 `crash_marker` 还是新机制）、
   对照组的配置（outbox on/off × 下游幂等 on/off 取哪两格）。
5. **可观测后端的交付方式**：Docker 不可用时的退路（本地 JSON 渲染 / Grafana Cloud /
   只用既有 JSON 导出给读者自己看）——本条需要所有者拍板，不要自行决定。

## 8. 边界纪律（触碰即停、上报）

* 出现"服务化 / 平台 / 生产级 / 高可用"口径，或任何对外可靠性暗示；
* MCP 服务需要监听非本地地址、需要鉴权或多租户；
* 内核依赖增加（必须进 extra）；
* `verify` 作业时长显著增长（> 5 秒）而无取舍说明；
* 为了集成而修改、绕过或"临时关掉"七步管线中的任何一步；
* 崩溃演示只报"1 次"而没有对照组；
* 需要真实 API key 的用例混入默认 `pytest`。
