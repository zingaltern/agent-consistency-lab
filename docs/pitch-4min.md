# 项目介绍口径（3–5 分钟，讲给听不懂的人）

> 目标：一个不懂 AI 的人听完能复述出"你给 Agent 配了日志、闸门、账本，证明它出错时不出事"。
> 原则：**先讲后果，再讲技术；每个技术词都配一句大白话；最后一定要落到"这值多少"**。

---

## 一、完整版（4 分钟，照着念都行）

### 0:00–0:30 一句话 + 一个比喻（钩子）

> "我用八周做了个东西，一句话说：**给 AI 配了一名新员工上岗要有的三件套——一本不能涂改的工作日志、一道大额操作要人点头的闸门、一本把花销算清的账簿。**
>
> 为什么是这三件？因为现在的 AI 能力很强，但它会犯错。真正卡住 AI 上岗的，从来不是它不够聪明，而是**它犯错的时候，系统兜不住**。"

### 0:30–1:30 我做了什么（三件事，全用业务语言）

> "第一，**日志**。AI 每一个决定、每一次动手，都写进一本只能追加、不能修改的流水账。
> 好处是：出了事能复盘——它当时看到了什么、为什么这么干，一字不会变。这就像财务的账本，不许拿橡皮擦。
>
> 第二，**闸门**。删数据、改配置这类危险动作，绝不自动执行，必须有人点头。
> 而且闸门不是靠一份"危险动作黑名单"——黑名单总会过期；我是让**工具自己声明风险**，所以哪怕模型今天发明了一个新的危险操作，它照样会被拦下来。
>
> 第三，**账本**。AI 每思考一步都要花钱，我按用途分桶记账（主流程、摘要、判分各多少），
> 让管理者能看清"这件事花了多少钱"，而不是月底看到一张糊涂账。"

### 1:30–2:30 我怎么证明它有用（这段是可信度的来源）

> "光说自己设计得好没有意义，所以我做了两件事证明。
>
> 第一件，**拔电源测试**。我在六个关键位置真的把进程 `kill -9` 掉——不是模拟异常，是真杀进程——
> 一共杀了 80 次。然后看两件事：**它能不能接着干完**，以及**会不会把已经干过的活再干一遍**。
> 结论是我最想讲的一点：**重复干活这件事，光靠 AI 自己防不住**——当崩溃发生在'操作已经做完、但还没来得及记账'的那一瞬间，系统根本不知道自己做没做过。
> 我的解法是：动手之前先记一笔"我准备做",做完再改成"做完了"；恢复时看到"准备做"就先去核对，绝不自己重做。这样把"悄悄做了两遍"变成"一条待核对的记录"。
>
> 第二件，**同一套考题跑四种做法**：老式规则脚本、一次性问 AI、用主流框架 LangGraph 搭的、还有我自己写的这套。
> 64 道题、每道题跑三遍，用统计方法比。
> 结果里有两个我一开始没想到的发现：
> 一是**三条读证据的路线，诊断准确率完全一样**——差别不在聪明，而在"证据看全了没有"和"出错时有没有人把关"；
> 二是我故意放了一个'橡皮图章'式的审批人（永远点同意），结果有闸门的路线和没闸门的路线出事率**一模一样**。
> 所以我在报告里写的结论是：**闸门决定的是"有没有人把关"，不是"会不会出事"**——这句话比"我做得多好"更有用。"

### 2:30–3:30 价值（分三层，按听的人关心什么说）

> "这东西的价值我分三层说：
>
> **对业务/管理层**：AI 从'不敢让它碰真东西'变成'可以在有护栏的前提下让它干活'。
> 因为它出错时，你要么收到一张待批工单，要么看到一条待核对记录——而不是第二天早上发现线上多了一次操作。
>
> **对团队/工程**：这三件事（不可涂改的日志、工具自述风险的闸门、分桶成本账）是可以直接搬到任何 Agent 项目上的。
> 我甚至保留了和主流框架的对照数据，能说清'什么时候该用框架、什么时候该自己写'。
>
> **对我个人**：我原本是后端工程师，这个项目的定位很清楚——
> **不是让 AI 更聪明，而是让系统在 AI 不聪明的时候不出事**。
> 这正好是大厂现在急缺的那类人：JD 里叫 'Agent Harness' 或 'Agent 运行时'，做的事就是我这八周做的事。"

### 3:30–4:00 收尾（诚实 + 抛回问题）

> "最后说边界：**这是一个实验台，不是生产系统**。场景和模型都是我合成的，没有真实流量，
> 所以我不报'提升了百分之多少'这种数——我报的是'同一套考题上四种做法的差距，带误差范围'。
> 我知道它还缺什么：掉电场景、多进程并发、真实模型接入，这些我都写在文档的未决清单里。
>
> 演示只要一条命令，从告警进来到全流程回放。**要不要我现在跑给你看？**"

## 二、禁词表（讲了就会把人讲晕）

| 别说 | 改成 |
|---|---|
| Agent / LLM | "会自己拿主意的程序"、"AI 新员工" |
| 事件日志 / append-only | "不能涂改的流水账" |
| checkpoint | "存档点" |
| 幂等 / idempotency key | "每笔操作的唯一编号，防重复" |
| outbox / 意图行 | "动手前先记一笔'我准备做'" |
| kill -9 / chaos injection | "拔电源测试" |
| 门禁（gate） | "上线前的自动检查" / "发布闸门" |
| 消融 / ablation | "同一套考题跑四种做法" |
| 配对置信区间 | "同一道题比出来的差距，带误差范围" |
| RAG / 上下文工程 | "让它每次只看该看的东西，省脑子也省钱" |
| Harness | 只说一次英文，马上翻译成"AI 上岗要配的那套管理机制" |

## 三、30 秒电梯版

> "现在 AI 能干活，但企业不敢让它碰真东西，因为它会犯错、且出错时系统兜不住。
> 我做了三件事：不能涂改的操作流水账、危险动作必须人点头的闸门、按用途分桶的成本账。
> 然后用真杀进程的方式测了 80 次崩溃恢复、又用同一套考题比了四种做法。
> 结论是：防重复不能靠 AI 自己，得靠记账和核对；闸门的价值是'把人拉回回路'，不是'让事故消失'。
> 这套东西正好就是大厂在招的 Agent 运行时岗做的事。"

## 五、三个可以随时掏出来的数字

| 数字 | 说人话 |
|---|---|
| 80 次真杀进程、六个位置、重复副作用为 0 | "拔了 80 次电源，没把活干重过" |
| 有闸门 0% vs 无闸门 20.8% 的破坏性操作执行率 | "同一道题，有闸门的没出事，没闸门的五分之一出了事" |
| 压缩后成本 +79%（33% → 100% 完成率） | "让它干得完，是要多花钱的——这笔账我算清了才敢用" |

## 六、听众最可能问的五个问题（大白话答案）

| 问题 | 白话回答 |
|---|---|
| "这不就是调 API 吗？" | "调 API 谁都会。我这八周在解决'调完之后怎么不出事'：崩溃了怎么办、模型说要删库谁来拦、花销怎么算。" |
| "市面上不是有现成框架？" | "我用了，而且是当对照组用的。同场景下它和我的写法准确率一样，差别在我的版本能撑住'拔电源'，并且闸门挂在工具风险声明上而不是黑名单上。" |
| "你这些数据是真的吗？" | "是合成的场景和脚本模型，所以我从不报百分比提升，只报'同一套题四种做法的差距 + 误差范围'。所有数字都能一条命令复现，报告和数据都在仓库里。" |
| "对我们有什么用？" | "三件事可以直接搬到你们现在的 AI 项目上：操作流水账、危险动作闸门、成本分桶。另外我保留了'什么时候该用框架'的对照数据，可以省你们一周的选型。" |
| "你会写业务代码吗？" | "我原本就是后端。这个项目的日志、状态机、权限、事务一致性，全都是后端的老手艺——只是这次上面挂的是 AI。" |
