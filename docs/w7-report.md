## 一、为什么必须"扫阈值"而不是只做"开/关"

W4 得出"压缩抬高净成本"，但那来自**退化触发**：固定 13k 的余量在小窗口下让
`should_compact` 恒真、每一步都压。要回答"压缩值不值"，必须在阈值这个维度上扫一遍，
看**完成率 / 缓存命中 / 净成本**三者的联合形状——这才是计划里说的那条三维曲线。

**方法**（沿用 W6 立下的规矩）：

* 8 个长任务变体（取证轮数 6–11、日志体量 30–60 行），**dev 6 个用于选点、holdout 2 个只做确认**；
* 6 档阈值（`off` + 0.95 / 0.85 / 0.70 / 0.50 / 0.30），每格跑 2 次完整周期（run→approve→resume）；
* **统一口径**：一律不卸载（把"压缩"这一个变量隔离出来）、同一 token 估算与价格表、
  指标全部从事件日志推导（与 W5/W6 同源）；
* 选点规则**写死在代码里**：先满足最高完成率，再比成本——不允许"看图挑最好"。

## 二、结果（dev，n=12/档）

| 压缩阈值 | 完成率 | 平均压缩次数 | 平均输入 token | 缓存命中率 | 平均净成本 | 溢出 |
|---|---|---|---|---|---|---|
| **off** | **33%** | 0.00 | 46,898 | **68.0%** | **$0.06608** | 8 |
| **0.95** | **100%** | 1.33 | 49,492 | 52.8% | **$0.09273** | 0 |
| 0.85 | 100% | 1.33 | 49,492 | 52.8% | $0.09273 | 0 |
| 0.70 | 100% | 1.33 | 48,907 | 51.8% | $0.09329 | 0 |
| 0.50 | 100% | 3.00 | 40,396 | 33.8% | $0.09836 | 0 |
| 0.30 | 100% | 6.67 | **33,964** | **7.0%** | **$0.10910** | 0 |

**holdout 确认**（只在 `off` 与选定阈值 0.85 上各跑 4 次）：

| 压缩阈值 | 完成率 | 缓存命中率 | 平均净成本 |
|---|---|---|---|
| off | 50% | 71.8% | $0.09799 |
| 0.85（dev 选点） | 100% | 60.2% | $0.12030 |

### 结论

1. **压缩买的是完成率，不是省钱**：不压缩时只有 33% 的变体能跑完（8 次溢出），
   成本最低（$0.066）但任务失败；压缩后完成率 100%，成本涨到 $0.093（**+40%**）。
   "先满足完成率、再比成本"的选点是 **0.95**（与 0.85 同价），holdout 上方向一致
   （50% → 100%，成本 +23%）。
2. **压缩次数与缓存命中率严格反向**：0 次压缩 68.0% 命中 → 1.33 次 52.8% →
   3 次 33.8% → 6.67 次 **7.0%**。每一次压缩都从替换点击穿前缀缓存，
   这条在阈值维度上第三次被证实（W4 单点、W5 交叉对照、W7 全曲线）。
3. **"压得越早越省 token"是真的，但省下的 token 不值那些缓存写溢价**：
   输入 token 从 49,492 降到 33,964（-31%），而净成本从 $0.09273 涨到 $0.10910（**+18%**）。
   这是本轮最实用的工程结论：**阈值应贴近上限（0.85–0.95），而不是"早点压更安全"**。
4. **阈值在 0.95 与 0.85 之间没有差别**——本工作负载的上下文是"成块跳变"的
   （每轮日志一次涨一大截），所以两个阈值落在同一个触发点上。含义：阈值不是连续旋钮，
   在有明显块状增长的任务里它的可调空间很窄。

## 三、trace 收口（`harness/trace.py`）

原来计划的 "OTel spans + 看板" 在评审里被砍成"console exporter + 查询脚本"，
这一轮把这部分补齐了，并明确了一个更重要的架构选择：

> **事件日志是权威，trace 是投影。** 不是"边跑边打 span"（那会有两套事实、
> 崩溃后无从对账），而是从事件日志**离线投影**出 span 树——因此 trace 与语义永远一致，
> 可以重放、可以对历史 run 补投影。

Span 形状（属性名向 OTel GenAI 语义靠拢，但不假装实现了该规范）：

```
invoke_agent <run>                 ← 根 span（汇总成本/预算）
├── chat scripted-model            ← 每次模型调用：tokens_in/out、cache_read/write、cost、view 指纹
├── execute_tool scale_pool        ← 每次工具调用：效果类别、幂等键、结果状态、error.type
├── human_approval                 ← 每次审批：interrupt id/index、决策、参数 hash、actor
├── compact                        ← 每次压缩：替换数、前后 token、原因、轮次
└── error <class>                  ← 错误事实（零时长，便于检索）
```

用法：

```bash
# 人类可读的 span 树（排障时比翻事件日志快）
.venv/bin/python -m harness.trace --run-dir /tmp/w7-trace
# OTel 形状的 JSON（接真实后端时替换成官方 SDK 即可）
.venv/bin/python -m harness.trace --run-dir /tmp/w7-trace --otel
```

两处诚实标注写进了代码与测试：

* 模型调用没有独立的起止事件，chat span 的时长是**推导值**（起点取上一个事件之后），
  属性里带 `harness.duration_is_derived=true`；
* 没有接预算账本时，根 span 的成本从 chat span 汇总，并标 `budget.source=derived_from_chat_spans`。

## 五、边界与未决

1. **仍是模拟推理器 + 合成变体**：本报告的"完成率"是"任务能否跑完（不溢出）"，
   **不是回答质量**；质量维度要等接真实模型。
2. **压缩摘要用的是确定性桩**（`deterministic_summary`），因此"摘要质量"不在变量里；
   真实摘要模型可能压得更狠或更差，那条曲线会移动。
3. 扫描只覆盖 6 档阈值 × 8 个变体，未扫 `keep_recent_groups`（另一个压缩旋钮）
   与"摘要模型选择"，二者都留作后续。
4. holdout 只跑了 2 档 × 4 次，样本小（Wilson 区间在报告 JSON 里可查），
   它的作用是"方向确认"而不是精确复现。
5. 掉电语义、多进程并发仍不在范围内（沿用 W2–W4 的边界声明）。
