# 长文①：Agent runtime 到底承诺什么——50 次 kill -9 之后我改掉了自己的三个说法

> 本文是实验记录，不是规范。所有数字都能在本仓库用一条命令复现（见文末）。
> 场景与模型都是**合成**的：受控仿真世界 + 确定性脚本模型，没有真实流量。

## 一句话结论

**一个 Agent runtime 对"副作用"唯一能诚实承诺的是 at-least-once。**
"至多一次"要么来自下游幂等，要么来自你自己实现的 outbox + 对账；
把它写进 runtime 的承诺清单里，就是在某处悄悄依赖了下游。

## 一、起点：一个看起来无懈可击的恢复算法

我最初的设计是这样的（也是很多教程的写法）：

1. 每一步把状态写进 checkpoint（thread_id + checkpoint_id + parent）；
2. 崩溃后从最新 checkpoint 恢复，重放其后的 writes；
3. "已完成的任务不会重跑，未完成的任务从头重跑"。

测试全绿，文档写得很自信。然后我把崩溃注入从"模拟抛异常"换成**真实的 `kill -9`**，
并且给每个注入点起了名字：

```python
# harness/loop.py（简化）
append(tool_call_event)  # 1. 记录决策
chaos.hit("pre_tool_exec")  # 窗口 1：执行前被杀
result = tool.fn(args, key)  # 2. 真实副作用发生在这里
chaos.hit("post_tool_effect_pre_record")  # 窗口 2：效果已发生、任何记录都没有
append(tool_result_event)  # 3. 权威记录
record_idempotency_row(result)  # 4. 去重行
chaos.hit("post_record_pre_commit")  # 窗口 3：记录齐全、checkpoint 未提交
```

## 二、矩阵跑完，三个说法倒下

矩阵：3 个窗口 × runtime 去重开/关 × 下游幂等开/关 × 5 次 = 60 次真实 SIGKILL + 60 次恢复。
裁判不是 runtime 的日志，而是**外部副作用账本**（独立 SQLite，每次真实执行无条件追加一行）。

### 说法一："加上幂等键，重复就解决了"——错

窗口 2（效果已发生、记录未落盘）下：

| 配置 | 出现重复副作用 | 单键最大效果数 |
|---|---|---|
| 无 outbox、下游不幂等 | **5/5** | 2 |
| 无 outbox、下游幂等 | 0/5 | 1 |
| runtime 去重开/关 | **不改变任何一格** | — |

原因很朴素：**崩溃点在记录之前，rekey 表里根本没有可查的行**。
所以"加了幂等键就安全"在崩溃一致性上是错的——键只在你**已经知道**这是一次重试时才起作用。

### 说法二："恢复时重放 writes 就不会重跑"——对，但代价是我没说的

`post_record_pre_commit` 窗口（记录齐全、checkpoint 未提交）确实能恢复到恰好 1 次效果：
因为**事件日志是权威**，重放时能看见"这次调用已有结论"。但它同时暴露一件我没写进文档的事：

> 我文档里承诺的恢复算法（从 checkpoint 重放 writes）**在代码里从来没被调用过**。
> 真实恢复路径是"折叠事件日志 + 重跑未闭合调用"。

这是独立审计抓到的（三路审计一致指出）。修法不是把死代码接上，而是**把文档改成事实**：
checkpoint 降级为"边界快照 + 交叉校验"，恢复权威归还给事件日志。

### 说法三："50 次 kill 全部通过"——这句话本身有毛病

- 按 rule of three，50 次 0 失败只把失败率上界压到约 6%，不是"100% 无重复"；
- `kill -9` ≠ 掉电：SQLite 在 `WAL + synchronous=NORMAL` 下，进程被杀时 OS page cache 还在，
  但**掉电会丢最后一个已提交事务**。所有结论只对 kill -9 成立，这条现在写在语义文档第一节。

## 三、修法：把"看不清的状态"变成显式状态

窗口 2 的根因不是策略问题，而是**信息缺失**：崩溃后 runtime 无法区分
"这次写没执行"与"执行了但没记下来"。三条路，我选了第三条：

1. 依赖下游幂等（实测有效，但把一致性外包给了别人）；
2. 猜（不可接受）；
3. **outbox：把记录提前到执行之前**——
   先写一行 `pending` 意图 → 执行 → 闭合成 `executed`；
   崩溃后遇到 `pending`，**先探针对账，绝不自动重跑**。

修完再跑同一个矩阵：

| 窗口 2 的配置 | 重复副作用 | unknown 待对账 | 恢复方式 |
|---|---|---|---|
| 无 outbox | **5/5** | 0 | 重跑 → 重复 |
| outbox + 下游支持按键读回 | **0/5** | 0 | 探针确认已生效 → 重放不重跑 |
| outbox + 下游**不**支持读回 | **0/5** | **恰好 1 行** | 标记 unknown，交人工 |

第三条是最有意思的结果：**它没有消除崩溃窗口，而是把"静默重复"变成了"有界、显式的未知"**。
前者的后果是线上多了一次扩容（没人知道），后者的后果是一条待对账工单（有人知道）。
工程上这是完全不同量级的事故。

## 四、我现在的承诺清单（可以拿去对账）

| 承诺 | 内容 |
|---|---|
| 执行语义 | at-least-once：崩溃后未完成的步骤会重新执行 |
| 效果语义 | **至多一次仅当下游支持幂等键或读回**；否则产生 `unknown`，进入对账 |
| 日志语义 | 不重不漏（同一事件不重复写入、已提交事件在 kill -9 语义下不丢） |
| 状态语义 | 状态不作为权威持久化，只有事件日志是权威 |
| checkpoint | 边界快照与交叉校验；**不是**恢复权威 |

以及三条明确**不承诺**：不承诺 exactly-once 效果；不承诺掉电不丢最后一个事务；
不承诺跨进程并发写（租约事件已登记但未实现——这条也在文档里）。

## 五、如果你要做同样的事

1. **裁判必须是外部的**：用副作用账本（或真实下游）计数，不要用 runtime 自己的日志；
2. **注入点必须命名**：随机 kill 只能证明"你测过的那几个位置没问题"；
3. **把承诺写成可执行的清单**：本仓库的 `docs/semantics.md` 就是这份清单，
   审计是照着它逐条对账的；
4. 诚实标注统计边界（n=5 与 n=192 是两套口径，别混引）。
