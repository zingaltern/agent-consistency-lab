# 项目介绍口径（技术面试官版，3–5 分钟）

> 听众画像：互联网大厂 / AI 公司的技术面试官，有 AI 基础，知道 LLM、RAG、Function Calling、
> LangGraph，但**没听过你的项目**。
> 因此：术语可以直接用，但**每个术语出现时给半句锚点**（它解决什么问题）；
> 不解释"什么是大模型"，但也不假设他知道"outbox 意图行"是什么。
> 结尾必须落到"这值多少"和"我为什么能把它做出来"。

---

## 一、主稿（4 分钟，按分钟标注）

### 0:00–0:40 背景与痛点（讲行业共识，不讲自己的项目）

> "我做的题目是：**让 Agent 从 demo 走到能上生产**。
>
> 现在大模型的 reasoning 和 tool use 都够用了，真正卡住落地的是工程侧的三件事，
> 也是我从 JD 和公开案例里反复看到的：
>
> 一是**不可逆操作没人敢放**。模型一次误判就可能删库、改配置、多发一笔钱，
> 所以很多公司宁可把 Agent 停在"只读 + 建议"，不接写操作。
>
> 二是**长任务的状态没人兜得住**。Agent 一跑几十步、中间要等人审批、进程还可能崩，
> 崩了之后能不能接着跑、会不会把已经执行过的副作用重来一遍——这是分布式系统问题，
> 不是 prompt 问题。
>
> 三是**成本不可归因**。一次任务要调好几次模型、还有摘要、判分、重试，
> 不分桶记账，月底只能看到一张糊涂账。"

### 0:40–1:20 挑战（说清"为什么难"，这段决定后面成就的分量）

> "我自己动手之后，发现难的不是把 loop 写出来——两百行就能跑通——难的是三件事：
>
> **第一，崩溃窗口是不可枚举的。** 你把'工具执行完'和'结果落盘'分成两步，
> 两步之间就有一个窗口；在那个窗口崩溃，系统根本不知道自己做过没有。
> 这个窗口靠加锁、加重试都消不掉，只能靠**语义设计**。
>
> **第二，人工审批的语义比想象的细。** 批准的是'某一次调用 + 某一组参数'，
> 不是'这类操作'。一旦批准之后参数被改了、或者模型重发了同一个调用，
> 会出现'批准 A 执行 B'或者'改了参数却命中旧的幂等键'这类静默错误。
>
> **第三，也是最难的：怎么证明它有用。** 自己没有流量、没有真实用户，
> 很容易做成'自己出题、自己判卷'——这是我认为这个项目最大的技术风险，比写代码难。"

### 1:20–2:40 我做了什么（架构 + 关键设计决策 + 取舍）

> "我做了三层，都是自研内核 + 现成件复用：
>
> **第一层，运行时内核。** 事件日志是唯一权威——扁平 append-only，历史改写被数据库触发器
> 物理禁止；状态永远是日志的折叠物，不持久化权威状态。checkpoint 只做边界快照和交叉校验。
> 工具执行走 outbox 三态：**先写 pending 意图 → 执行 → 闭合成 executed**；
> 崩溃后遇到 pending 不自动重跑，先探针对账，对不上就落成 `unknown` 交人工。
>
> **第二层，治理层。** 审批门挂在**工具自己声明的风险**上，不是动作名黑名单——
> 这样模型今天发明一个新危险操作也拦得住。审批记录绑定 (tool_call_id, 参数哈希, 过期, scope)，
> 执行前用实际参数二次校验堵 TOCTOU；改参就换新调用、新幂等键、新审批。
> 另外做了上下文工程：视图纯函数重建、大结果内容寻址卸载、压缩以事件追加不改写历史、
> 成本按 main/compaction/judge 分桶记账。
>
> **第三层，可观测与验证。** 事件日志投影成 span 树（OTel 语义的命名），
> 任意历史 run 可以回放；评测侧有 64 个合成故障场景、四条技术路线对照、
> 配对 bootstrap 区间和一套**可执行门禁**——门禁里还包括'实验假设自检'，
> 比如'如果无闸门的路线不再出事，说明我的场景集失去区分力，CI 必须变红'。
>
> 一个取舍我想特别说：我**没有**用 LangGraph 当运行时，而是自己写了内核，
> 同时把 LangGraph 当作**对照组**跑同一套场景。这样我能回答'为什么不用框架'——
> 不是不用，是当基线用；同场景下两者步数、token、准确率完全一致，
> 我多拿到的只有崩溃一致性和'工具自述风险'这两层。"

### 2:40–3:30 成就（数字 + 制度化 + 自我证伪）

> "成果我分三类讲，因为我觉得单一数字最容易被追问穿。
>
> **一类是可复现的量化结果。** 六命名崩溃窗口 × 16 格 × 5 次，一共 80 次运行，
> 其中 **70 次注入了真实** `kill -9`（篡改对照与长任务对照两格按设计不注入），
> 裁判是外部副作用账本而不是我自己的日志：
> 唯一会丢一致性的窗口是'效果已发生、记录未落盘'；关掉 outbox 时重复副作用 5/5 复现，
> 开启后 0/5——有读回能力时探针确认、没有时收敛成恰好一行 `unknown`。
> 评测侧 64 场景 × 4 路线 × 2 推理器人格 = 1536 次运行：
> 三条读证据的路线诊断准确率**完全相同**（90.1% / 61.5%，配对 CI 恰好 [0,0]），
> 差异只在'出错时会不会执行破坏性动作'——无闸门 20.8%，有闸门 0%。
> 成本侧：压缩阈值扫描显示压缩让完成率 33% → 100%，但净成本 +79%——
> 因为每次压缩都从替换点击穿前缀缓存。
>
> **二类是制度化。** 208 个测试、CI 跑 3.11/3.12 双版本、14 条门禁（含最小样本量和
> 实验假设自检）、全部结论一条命令复现。这部分的意义是：**别人可以自己验证我，不用信我。**"

### 3:30–4:10 他人评价与诚实边界（这段最容易被忽略，但最能加分）

> "评价这块我必须说清楚，因为它也涉及数据诚实：
>
> 我做了一轮**对抗性审计**：五路 + 四路，共九个只读审计代理，任务是'找出会让结论不成立的问题'，
> 每条结论都要核到代码或文档证据。它们抓到了 7 个 P0，其中三个是真正打脸的：
>
> 一是**我的恢复算法在文档里承诺了、但代码从来没调用过**——文档写'从 checkpoint 重放 writes'，
> 实际恢复走的是日志折叠，我把文档改成事实、checkpoint 降级为交叉校验；
> 二是**跨系统比较被种子污染**——种子里含系统名，导致'某框架被拦下 29.7% vs 我的 20.3%'
> 其实是哈希伪影（零假设下 p=0.0009）；改成共同随机数后三条路线准确率完全一致；
> 三是**我最得意的结论被自己的消融推翻**：我补了一个'读满四通道的规则引擎'对照，
> 它 100% 正确、更便宜，严格支配了我的 LLM 路线——
> 也就是说在这个场景集上，'agent 比规则强'不成立，真正的边界是
> **证据通道和动作空间能不能预先枚举**。
>
> 所以我说'评价'时只敢说：这些是**对抗性评审代理 + 制度化门禁**，不是真人专家背书。
> 我另外写好了一份黑盒测试提示词（明确告诉测试者哪些可读、哪些是'答案'不能先看），
> 准备找真人测一轮——我把它当成这个项目下一步的工作项，而不是已经拿到的荣誉。"

### 4:10–4:30 收尾（一句话价值 + 抛回问题）

> "总结一句：**我做的不是让模型更聪明，而是让系统在模型不聪明的时候不出事**——
> 日志、闸门、账本、评测，这四件事正是大厂 Agent 平台岗 JD 里逐条写的内容。
> 演示只要一条命令，从告警进来到全流程回放，要不要现在跑一遍？"

## 二、术语锚点表（技术听众版，不是禁词表）

| 术语 | 出场时配的半句锚点 |
|---|---|
| at-least-once | "执行语义只能承诺至少一次，至多一次要么靠下游幂等、要么靠对账" |
| outbox / 意图行 | "动手前先写一笔 pending，恢复时看到 pending 不重跑、先对账" |
| checkpoint | "只做边界快照和交叉校验，不是恢复权威——权威是事件日志" |
| TOCTOU | "批准时和执行时参数可能不一致，所以执行前用实际参数重算哈希" |
| 前缀缓存 | "供应商按最长公共前缀计费：读 0.1×、写 1.25×，所以前缀不能有易变内容" |
| 消融 | "同一批场景跑四种做法，用配对区间比差值，而不是比绝对值" |
| LangGraph 对照 | "当基线用：同场景能力等价，差异在崩溃一致性与工具自述风险" |
| 门禁 | "CI 里的可执行检查，包括'如果我的实验失去区分力就变红'这种自检" |

**不要展开超过一句的东西**：Transformer 细节、具体 prompt 写法、某个框架的 API 用法——
面试官不会顺着这些问，反而会把你带偏。

## 三、三个"成就卡片"（被追问时掏出来）

| 卡片 | 数字 | 一句话解释 |
|---|---|---|
| 崩溃一致性 | 16 格 × 5 次 = 80 次运行、70 次真实 `kill -9`、重复副作用 0 | 唯一危险的窗口是"效果已发生、记录未落盘"，outbox 把它变成一行待对账的 unknown |
| 架构消融 | 1536 次运行、三条路线准确率 CI 恰好 [0,0]、无闸门 20.8% vs 有闸门 0% | 诊断能力没有架构差异；闸门决定的是"有没有人把关"，橡皮图章下两条路线出事率一模一样 |
| 成本会计 | 压缩：完成率 33% → 100%，净成本 +79%（压缩桶占 22–25%） | 命中率不是目标函数，压缩是拿钱买可用性；卸载才是唯一纯赚的杠杆（token −66%） |

## 四、技术面试官最爱追问的八个问题（准备好答案）

| 追问 | 答案要点 |
|---|---|
| 为什么是 at-least-once 而不是 exactly-once？ | 因为副作用在外部系统，runtime 无法原子地"执行 + 记录"；exactly-once 必须由下游幂等或读回参与，否则只能收敛成 unknown |
| 为什么不用 Temporal / DBOS 这种 durable execution？ | 它们能解决恢复，但解决不了"效果已发生、记录未落盘"这个窗口——那需要下游幂等或读回；另外我的学习目标就是把这套语义自己实现一遍，对照结论写在报告里 |
| 你的评测是不是自证？ | 是最大的风险，所以我做了四件事：场景来源声明、冻结 holdout、多种评分口径、以及把"实验假设"写进 CI 门禁；并且我主动报告了三个自证陷阱 |
| LangGraph 对照公平吗？ | 同一批场景、同一推理器、同一计费口径；代码量 95 行 vs 340 行，能力等价；我还把"迁移清单"写进了报告 |
| 样本量够吗？ | 每格 192 次，报告配对 MDE（80% 功效约 9%），小于它的差距我明确写"不可区分" |
| 有没有真实流量？ | 没有，所以我不报百分比提升，只报相对基线的差值 + 区间；这条写在报告第一页 |
| 最难的 bug 是哪个？ | 三个：视图渲染器在审批点自毁配对（写操作的调用与结果被整段丢出模型视图）、幂等键不含 branch 导致分叉复用父分支的批准、压缩可能越压越大；都是审计抓的 |
| 如果给你三个月你会继续做什么？ | 掉电语义、多进程租约、artifact GC、接真实模型跑同一套评测、以及那轮真人黑盒测试 |

## 五、诚实提醒（讲这段时的分寸）

* **可以说**："九个审计代理抓到 7 个 P0""门禁能拦住我自己的退化""我被自己的消融推翻过一次结论"。
* **不能说**："某大厂专家评价过""有真实用户在用""线上验证过"。
* 如果面试官问"这些评审是 AI 做的吧"——**直接承认并加分**：
  "是，九个只读审计代理，结论都核到代码证据；真人测试的提示词我已经写好，还没跑完。
  我更在意的是：它们抓到的三个问题都是真的，而且我修了、固化成回归测试了。"
