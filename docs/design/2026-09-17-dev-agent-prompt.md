## 3. 第三步：执行顺序（一个里程碑一个分支）

**顺序：A-M1 → A-M2 → A-M3 → B-M1 → B-M2 → B-M3**。
理由见 B §7：B 每一步都会产出新的"结论数字"，先立起 A 的数字再生机制（claim 门禁），
B 的验收数字才能天然被覆盖。

每个里程碑严格执行：

```bash
git switch main && git pull
git switch -c <feat|fix|exp|audit|chore>/<slug>     # 一个里程碑一个分支
# 只做该里程碑范围内的需求，不做顺手重构、不做范围外"优化"
# 跑门槛（见 docs/development.md §2.3）：
.venv/bin/pytest -o addopts= -p no:cacheprovider -q     # 必须全绿
.venv/bin/ruff check .
.venv/bin/python -m experiments.crash_matrix --repeats 5        # 涉及崩溃/恢复语义时必跑
.venv/bin/python -m opsenv.suite --per-fault 8 --repeats 3 --gate   # 涉及评测/统计/门禁时必跑
git add -A && git commit        # 中文提交信息，说清"为什么"
git push -u origin <branch>
```

**每个里程碑收口时停下汇报**（不要一口气推到底），汇报内容：

1. 分支名与提交清单；
2. 该里程碑验收门**逐条**结果（对照 A §6 / B §5 的表，逐条给出通过与否 + 证据命令）；
3. 新增/修改的测试与用例数（**用脚本计数，不许手写绝对数**）；
4. 未能满足的门（如有）及原因，以及你建议的处置；
5. 下一步计划。

汇报后等待确认，再开始下一个里程碑。合并由仓库所有者在网页端完成
（`main` 已/将开启 branch protection：你只负责推分支，不要尝试直推 `main`，
不要 force push，不要绕过保护）。

## 4. 硬性纪律（违反 = 返工）

1. **禁止直推 `main`**；禁止 force push；合并必须走 PR 并由所有者执行。
2. **现有能力不许回退**：`scripted` 模式默认行为零改变；现有测试必须继续全绿；
   现有 14 条门禁的**语义与阈值不许调整**（本任务只加新探测器/新机制，不改旧判定）。
3. **数字不许手写**：凡是"测试数量""注入次数""覆盖率"这类会漂移的数字，
   一律用脚本计数来源（`pytest --collect-only` 等）；文档里的每个数字都要能被命令再生。
4. **禁令清单（`docs/testing.md` §4）逐条有效**：真 SIGKILL、外部账本裁决（读账本连 `-wal`）、
   CRN 种子不含系统名、holdout 冻结、不得用 ground truth 喂被判定的机制、不得 mock 关键机制。
5. **live 路径不许进默认 CI**：真实 API key 只能出现在显式 `-m live` 标记的测试里；
   **录制文件与 key 不得写入任何仓库路径**。
6. **边界纪律**（A §7 与 B §8 逐条有效）：出现"生产级/高可用/服务化"口径、
   需要放宽语义、需要把远程服务变成默认路径——**立即停止该方向并上报**，不要自行决断。
7. **语义变更同步**：任何影响 `docs/semantics.md` 承诺的改动，必须**先改承诺清单**再改代码，
   并说明"旧承诺 → 新承诺"的差异。
8. **一个提交一件事**；脚本化批量改动必须逐条 assert；
   文档引用代码写相对路径 + 符号名，不写行号。
