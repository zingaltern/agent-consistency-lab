# 给外部测试人员的标准提示词

> 用法：把下面整段（从"任务"到"交付"）原样发给测试人员。
> 设计意图：**黑盒优先**——先读"规格"（承诺清单）而不是"答案"（报告数字与测试断言），
> 否则测出来的只是"作者写得对不对"，而不是"系统是不是真的这样"。

---

## 任务：对一个 Agent 运行时项目做独立测试（黑盒优先，结论必须可复现）

### 0. 你的角色与底线

* 你是**外部测试者**，目标是找出"声称与事实不符"的地方，不是让测试通过。
* 仓库**只读**：不要修改任何文件，不要 `git commit/push`，不要动 `reports/` 与 `docs/`。
  需要构造故障时，把仓库复制到 `/tmp` 再改。
* 所有实验产物写到 `/tmp`；**不联网**（项目本身不依赖网络）。
* 每条结论必须附**可复现命令 + 输出要点**；做不到就写"无法判定"，不要猜。
* 允许写临时脚本 import 项目模块（用仓库自己的 venv）。

### 1. 被测对象

* 路径：`/Users/zingaltern/Documents/Default Project/agent-consistency-lab`
* 它是什么：**面向崩溃一致性与治理语义的 Agent runtime 实验台**。自研精简内核作为被测对象与
  测量仪器；用真实 `kill -9` 做崩溃注入；用四系统对照（规则/单次调用/LangGraph/自研）
  做架构消融；所有指标以配对置信区间与可执行门禁呈现。
* 环境（Python 3.11–3.14 任一）：

  ```bash
  cd "/Users/zingaltern/Documents/Default Project/agent-consistency-lab"
  python3 -m venv .venv && .venv/bin/pip install -e ".[dev,eval]"
  ```

### 2. 可读 / 不可读（这一节请严格遵守）

#### 2.1 测试前**可读**（这是"规格"，测试要对着它逐条验证）

* `README.md`——定位、如何运行、如何复现全部结论；
* `docs/semantics.md`——**运行时承诺清单**，这是本项目唯一的对外规格；
* `docs/HANDOFF.md`——当前状态、跨轮次口径规则、未决清单；
* 所有源码与 docstring（`harness/`、`opsenv/`、`experiments/`、`examples/`），
  以及各命令的 `--help`。

#### 2.2 测试前**不可读**（这些是"答案"，先读等于抄答案）

* `docs/w2-crash-windows.md`、`docs/w3..w7-report.md`、`docs/posts/`、`docs/resume.md`；
* `reports/`（自动生成的报告表格与汇总数字，含 ground truth 与预期结论）；
* `tests/`（内含大量期望行为断言）。

**完成你自己的测试并给出结论之后，请再读这些材料**，并单独交一节
"我的结论与作者声称的差异"（这一节我们很看重，不一致的地方无论谁对都算发现）。

#### 2.3 任何情况下**不可改**

整个仓库只读；不得为了让用例通过而改动代码、数据或文档。

### 3. 必测项（按优先级，A 最高）

**A. 可复现性**
按 README 的"如何复现全部结论"跑全部命令，记录退出码与耗时；
报告任何一条失败、或产出数字与文档不符之处。

**B. 承诺验证（对规格逐条证伪）**
对着 `docs/semantics.md` 的承诺表与不变量清单（INV-001..007），逐条尝试构造反例。例如：
"历史改写被物理禁止"是否真的物理禁止（直接对数据库发 UPDATE/DELETE 试试）；
"状态从不作为权威持久化"是否有某处偷偷依赖了 checkpoint 的内容。

**C. 崩溃语义**
用命名窗口做崩溃注入（`CHAOS_WINDOWS` 环境变量 + worker 的 `--help`），
**用外部副作用账本（run 目录里的 `world.db`）核对副作用真实发生次数**，
而不是相信 runtime 自己的日志。尝试找到"文档说不会重复、实际重复"的窗口组合。

**D. 审批语义**
篡改参数（批准 A 执行 B）、改参（应产生新调用与新幂等键）、拒绝、过期四条路径；
确认"执行前用实际参数二次校验"是代码行为而不是文档承诺。

**E. 评测口径**
尝试绕过门禁（缩小样本量、关闭部分系统、给出空数据）；构造已知差异的数据，
检查区间估计是否覆盖真值、门禁是否按声称的规则拦下退化（可以故意在 `/tmp` 副本里
注入一个退化，看门禁是否变红）。

**F. 边界与诚实性**
检查 `docs/semantics.md` 里"明确不承诺"的清单，是否有某处实现偷偷承诺了它
（例如某模块实际上假设了 exactly-once 效果）。

### 4. 缺陷报告格式

每条缺陷：**标题 / 严重度 / 最小复现（命令 + 输出）/ 期望 vs 实际 / 建议**。
严重度定义：

* **P0**——某条结论不成立（数据或机制与声称不符）；
* **P1**——声称与实现不符，但结论仍成立；
* **P2**——文档/口径与事实不符。

另附两节：**无法判定的项**、**你认为没被覆盖的风险**。

### 5. 交付

1. 一份 Markdown 报告（含上述分节）；
2. 一份命令清单，使他人在干净环境能复现你的每一条结论；
3. 最后读完 2.2 的材料后，给出"与作者声称的差异"一节。
