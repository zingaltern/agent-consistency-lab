> **性质**：只出设计，**没有改任何代码**（本轮红线：不改 `harness/**`）。本文回答的是

> **状态**：下一轮候选（HANDOFF §十二 登记），不是已实现能力。

## 0. 第一性原理：租约解决的是"两个进程同时以为自己是写者"

事件日志解决的是"一个进程内的崩溃一致性"（真 SIGKILL 实测：见 `docs/w2..w3`）。
它解决不了的是**两个进程同时写同一个 run**——今天没有任何检查拦住这件事
（`docs/semantics.md` §3 已如实写明："runtime 的写路径尚未接入它……今天双进程写同一 run
仍然不被任何检查拦住"）。租约是这一层缺失的**入场条件**，不是新的状态权威：

* 权威仍是事件日志：租约状态 = 日志里最后一条 `lease` 事件的折叠物
  （`harness/lease.py::fold_lease`），**不新增第二张权威表**；
* 租约只回答"这个进程有没有写权限"，回答不了"两个进程同时写会不会坏"
  （那仍由外部账本 `world.db` 裁决，见 `docs/testing.md` §4-9）。

## 1. 接入点：三处候选，与各自漏掉的窗口

| 候选 | 位置 | 挡住什么 | 漏掉什么 |
|---|---|---|---|
| A. loop 写路径入口 | `harness/loop.py::start` / `resume` / `approve`（每次进入 `_drive` 之前） | "另一个进程正在跑同一个 run"这类整段冲突 | **不覆盖** MCP 服务进程（`integrations/mcp_server.py` 直接走 `ToolExecutor`，不经过 `Loop`）；也不覆盖同进程内两次 `resume` 交错 |
| B. 存储层追加 | `harness/store/sqlite_store.py::append_many` | 所有写者（loop、MCP、直接调 store 的脚本） | 每次追加都查一次租约（读日志 + 折叠），把成本压到最热路径；且存储层不该知道"进程身份" |
| C. 执行管线（`harness/execution.py::ToolExecutor.execute`）的 **TOCTOU 复核点**（第 5 步，`execution.py` 中 `actual_sha != binding.approved_args_sha256` 那一处） | 副作用**发生前**的最后一道闸门 | **唯一能挡住"副作用"这个不可回滚动作的位置** | 只覆盖写类工具调用；不覆盖"另一个进程同时改状态/写 checkpoint"这类冲突 |

**推荐：A + C 组合，且以 C 为底线。**

* **C 是底线**：本仓库最贵的东西是"效果已发生、记录未落盘"这个窗口（`docs/w2-crash-windows.md`）。
  在两个进程都通过审批、都读到同一份"批准"的情况下，唯一能救的是**副作用前一刻**的检查——
  那正是 TOCTOU 复核点已经站着的位置（语义上它与"参数是否被换过"是同一类问题：
  授权的前提已经失效）。放在这里还顺带满足语义文档 §2.5 的顺序：第 5 步在 **outbox 预写（第 6 步）之前**，
  所以"被租约拒绝"的调用在日志里是**被拒绝**，不是"未知"——与 `arg_policy` 拒绝的处置完全同形。
* **A 是必要的补充**：只挡 C 会留下"另一个进程在两次工具调用之间写 checkpoint/状态"的窗口。
  A 的位置选在 `_drive` 入口而不是每次 append（性能），代价是它**不覆盖 MCP 进程**——
  MCP 侧要接就接在同一处 `ToolExecutor`（C），并在 MCP 服务启动时 acquire。
* **不推荐 B**：把租约塞进 `append_many` 会让"写租约事件本身"也要持租约（自指），
  而且它挡不住副作用（那才是不可回滚的那一步）。这与 §3 现有措辞一致：
  "校验在 checkpoint 事务**之外**（先证权、后写）"。

**与 §2.5 七步管线的关系**：租约校验是**第 5 步旁边的一道附加闸**（同一处、同一时机），
不改变七步的顺序与每一步的语义；未持有租约时的处置与第 5 步的 `rejected` 同形
（`tool_result.status=rejected`、`error_class=lease_not_held`、不写 outbox 意图行、无副作用）。

**与后台对账的关系**：租约**不参与**对账。对账解决的是"这条 unknown 到底发生了没有"，
租约解决的是"你有没有资格让它发生"。两者不共用状态，也不互相替代——
租约到期不会把在途的 unknown 变成 `failed`（那会伪造结论）。恢复路径（`resume`）同样要先过 A：
**接管一个 run 必须显式 acquire**，而不是"谁先读到最后一条 lease 事件谁就接着写"。

## 2. 失败语义：默认必须是"拒绝"，而不是降级或仅告警

三档可选，逐条给出理由与本仓库的口径依据：

| 档位 | 行为 | 评价 |
|---|---|---|
| **拒绝（推荐）** | 未持有 / 已过期 / 被别人持有 ⇒ `LeaseNotHeld` ⇒ 该次调用 `rejected`，run 停在 `WAITING_HUMAN` 或按调用方处置退出 | 与 `harness/lease.py::LeaseNotHeld` 的既有契约一致（"调用方必须停下来，而不是再试一次就好"）；与审批拒绝同形；误报的代价是"跑不动"而不是"两个进程同时写" |
| 降级（只读继续） | 允许读、拒绝写 | 要区分"哪些工具算写"（`Effect.WRITE_NONIDEMPOTENT` / 幂等写）——这个信息**已经有了**；但降级会让"读到一半的状态"成为常态，而本仓库的视图是纯函数重放，读并不需要租约 ⇒ 收益不明 |
| 仅告警 | 记一条 `error` 事件继续写 | **不可接受**：这正是"静默放行"的形态（W3 教训：分支不可达 + 静默放行是同一类事故）。要记事件就记账，不要用它替代拦截 |

**默认关闭**：`enable_lease=False` 时行为**逐位不变**（今天的行为），理由是单进程场景下
租约是纯开销；开启必须显式（与 `--budget-usd` 拒启 live 录制、artifact GC 默认 dry-run 同一哲学）。

## 3. 对单进程默认行为的影响

* 默认（不开启）⇒ **零影响**：不新增事件、不新增字段、不变更时序；已有 481 个用例的
  语义与产物不变（口径见 claim `tests-collected`）。
* 开启后单进程的影响面（都是**显式**代价）：
  1. 每次进入 `_drive` 之前多一次"读日志 + 折叠最后一条 lease 事件"（O(1) 次查询，
     与 checkpoint 交叉校验同量级）；
  2. 每个写类调用在执行前多一次折叠查询（第 5 步旁边）；
  3. 续租需要显式调用或由调用方定时驱动（**本设计不做后台心跳**：后台线程会引入
     "进程活着但心跳停了"的新故障态，而本仓库的注入手段是真 SIGKILL——心跳停与进程死
     无法区分时，租约就不再是可判定的入场条件）。
* **过期接管仍不做**（语义文档 §3 已写明）：过期只意味着"没有有效持有者"，
  接管只能由显式 `acquire` 决定——否则"过期即接管"会让两个进程都以为自己是持有者。

## 4. 要改的 `semantics.md` 承诺条目（预告，不在本轮改）

| 位置 | 现在写的 | 接入后要改成 |
|---|---|---|
| §3「并发边界」 | "runtime 的写路径尚未接入它——也就是说'未持有 ⇒ 可读失败'只在调用方显式调用时成立" | 删除"尚未接入"，写明接入点（`execution.py` 第 5 步旁 + `loop._drive` 入口）、默认开关与失败语义 |
| §3「租约是入场条件」 | "不做过期接管、不做分布式协调" | **保持不变**（本设计不动这两条） |
| §2.5 七步管线 | 七步顺序 | 第 5 步旁补一句"（可选）租约校验：未持有 ⇒ rejected，位于 outbox 预写之前" |
| §1「明确不承诺」 | 不承诺跨进程并发写 | **保持不变**：接入租约后仍然不承诺并发**正确性**，只多了"未持有就写不进去"这道入场条件 |
| 变更记录表 | — | 追加一行（性质：**扩大**——新增一条机器强制的拒绝路径） |

**这不是小改动**：它把"跨进程并发不承诺"从"没人拦"变成"拦了一道，但仍不承诺正确性"，
属于语义文档 §3 的口径变化 ⇒ 按仓库纪律**必须先改语义文档再改代码**。

## 5. 代价：变异基线会整份不可比

`harness/execution.py` 与 `harness/loop.py` **都在** `pyproject.toml [tool.mutmut].only_mutate` 里，
而 mutmut 3.x 按**函数内序号**命名变异体 ⇒ 在这两个文件里加/删/改函数会让编号大范围位移：

| 影响 | 说明 |
|---|---|
| 变异体名字集合 | 会大量变化 ⇒ `reports/mutation_baseline.json` 的 `status_by_mutant` / `fingerprints` 对不上 |
| 门禁后果 | 提交时 `Mutation gate` 会报 `[vanished-from-results]`（旧条目整条不见）+ `[new-survivors]`，**这是预期行为**（盲区视野变了） |
| 处置 | 跑 `python -m scripts.mutation_check --update-baseline --allow-wider-baseline`（刷新守卫会要求显式放行，理由写进基线的 `refresh.widening_override`），并在 PR 里说明"改名来自接入点新增函数" |
| 刷新成本实测 | 本机全量重跑 **563.0 秒**（2026-09-26，`--max-children 4`，2050 个变异体）+ 指纹约 17 秒；CI 侧同量级（nightly run `36112304447` 的 mutation 作业 21 分 11 秒，预算 45 分钟） |

**折中方案（若下一轮只想先验证语义、不想动基线）**：把租约校验放在**新增的独立模块**
（例如 `harness/lease_gate.py`）+ 在 `ToolExecutor` 里以**一次函数调用**接入——
新函数会新增变异体（`[new-no-tests]` 依然可能红），但不会让 `execution.py` 里既有的
上千条变异体全部重编号。这笔账要在动手前算清：省下的是基线刷新与对账，代价是接入点
多一层间接（"谁在什么时候调用它"变得不显眼）。

## 6. 落地顺序（下一轮的最小可验证路径）

1. **先改语义文档**（§3 + §2.5 + 变更记录），再动代码；
2. 代码：`ToolExecutor.execute` 第 5 步旁加 `lease.require()`（默认关闭）；
   `loop._drive` 入口加同一道闸；两处都要有"改坏必红"的回归用例；
3. **三件套用例**：正常路径（持有 ⇒ 可写）；失败路径（未持有/过期/被他人持有 ⇒ `rejected`
   且**无副作用**，由外部账本裁决）；不变量（拒绝发生在 outbox 预写之前 ⇒ 日志里不是 `unknown`）；
4. **退化注入**：把租约校验改成"仅告警"⇒ 用例必须红（这条注入正是 §2 里否掉那一档的理由）；
5. **真双进程冒烟**：两个进程抢同一个 run，用外部账本核对副作用次数；
   结论只能写成"这一次注入下未观察到重复"，**不得**写成并发安全（`tests/test_lease.py`
   的 docstring 已写明这句话）；
6. 变异基线刷新 + PR 里写明夸大范围（哪些是"入场条件"，哪些仍由外部账本裁决）。

## 7. 本结论不适用的范围

* 本文是**设计**：接入点、失败语义、代价评估都**未实测**（唯一实测数字是变异基线刷新耗时
  563.0 秒与 CI 侧 21 分 11 秒，两者都带出处）。任何"接入后会更安全"的说法在实现前都不成立。
* 租约不提供**分布式协调**、不提供**过期接管**、不提供**时钟同步保证**
  （过期判定用本机时钟 `time.time()`；时钟回拨会让"有效"与"过期"打架，这一点未做实验）。
* 本设计**不改变**"双进程并发写的实际后果由外部账本裁决"这条口径。
