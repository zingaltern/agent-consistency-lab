# 长文②：批准的是什么——审批、改参与幂等键的语义

> 结论先行：**人工审批批的不是"这类操作"，而是"这一次调用 + 这一组参数"。**
> 把这句话写成代码之后，会顺带解决四个很容易踩的坑。

## 一、先定义"批准"的四个字段

一个能对账的审批记录至少要有：

```python
class ApprovalBinding:
    tool_call_id: str  # 批准的是哪一次调用
    approved_args_sha256: str  # 批准的是哪一组参数（哈希）
    decision: str  # approved / rejected
    expires_at: float  # 什么时候作废
    scope: str  # once（只此一次）/ session（同工具同参数可复用）
    nonce: str  # 审计标识
```

## 二、四个坑（每一个都有实测）

### 坑 1：批准 A、执行 B（TOCTOU）

审批通过后到真正执行之间，参数可能被别的东西改掉。修法只有一条：
**执行前用实际参数重算哈希并比对**，不一致就拒绝。

实测（`--tamper on` 的对抗用例，5 次重复）：批准后把 `size: 64` 改成 `72` ——
**5/5 拒绝执行、0 副作用、错误分类 `args_sha256_mismatch`**。

### 坑 2：改了参数却沿用同一个幂等键

如果下游按幂等键去重，那么"改参重试"在它眼里就是"同一次调用的重试"，
它会返回**第一次的结果**——你批准的 32 和实际生效的 64 之间，隔着一个静默的错误答案。

所以：**改参 = 新调用**。实测的语义：

```
原调用 tc_write_1  → 闭合为 superseded
新调用 tc_write_1__edit1（新 tool_call_id ⇒ 新幂等键）
批准绑定到新调用与新参数
账本里落的是改后的参数（size: 32），键与旧键不同
```

这条不是我发明的：Stripe 的幂等键语义就是"改参数即换键"，我在自己的手册里查到过，
但在项目里真正写下来才发现——**只有把"键 = hash(run_id, branch_id, tool_call_id)"
里的 branch 也带上，分叉场景才不会出现跨分支复用**（见坑 4）。

### 坑 3：把 nonce 做成一一次性闩锁

我最初的想法很自然："批准只能用一次，所以执行前把 nonce 标记为已消费。"
然后矩阵里出现了一个尴尬的格子：**批准后崩溃、恢复时任务永久卡死**——
nonce 已消费、调用未执行，重新验证必然失败，人也不会再批一次。

正确做法：**nonce 是审计标识，不是闩锁**。单次性由
`(tool_call_id, approved_args_sha256)` 绑定 + **调用闭合**隐式保证：
执行被记录之后调用就闭合了，不可能再用这个批准去执行第二次。
于是"批准后崩溃"这个窗口可以安全重试——实测 `post_approval_pre_exec` 窗口
5/5 恢复到恰好一次副作用，且**不需要重新审批**。

### 坑 4：分叉出来的分支复用了父分支的批准与执行

这是审计抓到的 P0，也是我完全没有预设的 bug：幂等键原本是
`hash(run_id, tool_call_id)`——不含 branch。于是分叉出的子分支上，
模型重新决策同一个 `tool_call_id`（比如"拒绝并人工处置"分支上又提了同一个扩容请求），
去重表里**命中了父分支那一行**：静默复用另一组参数的结果、并且**完全跳过审批门**。

修法两条并用：
1. 键纳入 `branch_id`（分叉是一次新的逻辑调用）；
2. 去重命中时**校验参数哈希**——这正是那个"旁路校验字段"存在的意义。

## 三、更根本的一问：gate 的价值到底是什么

做完上面四条，我一度很得意："有审批门的路线，红线动作执行率 0%"。
审计一句话把我问住了：**值班人读的 forbidden 列表，和你计算"红线指标"用的是同一份 ground truth。**
也就是说，"0%" 里混着"人永远正确"这个假设。

于是做了橡皮图章消融（`LazyOperator`：永远批准）：

| 系统 | 称职值班人 | **橡皮图章** |
|---|---|---|
| harness（有 gate） | 0.0% 红线 | **4.2% / 20.8%** |
| langgraph（有 gate） | 0.0% 红线 | **4.2% / 20.8%** |
| single_shot（无 gate） | 4.2% / 20.8% | 4.2% / 20.8% |

**橡皮图章下，有 gate 的系统与无 gate 的系统红线率完全相同。**
所以正确的表述是：

> gate 决定的是"**有没有人把关**"，不是"会不会出事"。
> 它把模型出错的后果从"线上事故"变成"一条待决策的工单"——
> 至于这个工单被认真看还是被随手批准，那是组织问题，不是架构问题。

顺带一个反直觉的推论：**审批门的存在性比审批规则更重要**。
因为规则会滞后（我们场景里放了一个静态拒绝列表里没有的新破坏性动作），
而"所有写操作都要人过一眼"这个规则不会。

## 四、把审批当一等公民的收益

把审批做成事件（`approval` artifact）+ 状态机（interrupt/resume）之后，
白拿了三样东西：

1. **可观测**：任何一次高危操作，都能从事件日志回答"谁、什么时候、批准了什么参数"；
2. **可回放**：trace 投影里 `human_approval` 是一个有决策属性的 span，
   排障时一眼看到"卡在等人批"还是"批了没执行"；
3. **可测试**：拒绝 / 改参 / 过期 / 篡改四条路径都是确定性用例，
   不需要真的找个人来点按钮。

## 五、清单

* 批准 = (调用, 参数哈希, 过期, scope)，不是"某类操作"；
* 执行前二次校验参数哈希（堵 TOCTOU）；
* 改参 = 新调用 + 新键 + 新批准；
* nonce 不是闩锁；单次性由调用闭合保证；
* 幂等键要含 branch（如果有分叉）；
* 别把"gate 拦住了事故"说成架构功劳——那是人的功劳。
