**数据**：`reports/w6_eval.json`（64 场景 × 4 系统 × 2 推理器 × 3 次 = 1536 次运行；
W6 起报告的 JSON 只保留汇总与门禁，逐次明细用 `--runs-out` 再生）｜
**依赖**：`langgraph 1.2.11`

## 一、交付了什么

| 交付物 | 落点 | 说明 |
|---|---|---|
| 场景集 | `opsenv/scenario.py` | 8 类故障 × 8 = **64 个场景**，按构造确定（同一 seed 得到同一批），划分 dev 48 / holdout 16 冻结 |
| 运维壳 | `opsenv/environment.py` | 四通道取证（metrics/logs/changes/resources）+ 9 个合法处置动作 + 7 个破坏性动作，全部声明需审批；场景判定"是否解除、是否踩红线" |
| 推理器 | `opsenv/policy.py` | 能力（competence）与气质（honest/guesser）可配；误判落到声明的混淆项上，一半概率给破坏性动作 |
| 三条基线 + 本项目 | `opsenv/systems.py` | `workflow`（规则+静态拒绝列表）／`single_shot`（一次读全部+无 gate）／`langgraph`（图 + MemorySaver + 静态断点审批）／`harness`（本项目 Loop） |
| 评测套件 | `opsenv/suite.py` | 四系统 × 两推理器人格 × 全场景，输出可比指标 |

**场景来源声明（最重要的边界）**：所有场景都是**合成**的。分类学参考公开的微服务故障模式
（连接池耗尽、慢查询、内存泄漏、磁盘写满、证书过期、坏发布、缓存击穿、下游超时），
但证据内容是生成的，**没有真实流量、真实事故数据或公开 Postmortem 数据集**。
代价是外部效度有限；换来的是 ground truth 客观、可复现、可冻结。

## 二、评测设计：让"架构差异"可测

1. **证据分四个通道，决定性证据只在一个通道里**，其余通道给出轻度异常信号指向一个
   *似是而非的混淆项*（例如内存泄漏场景的指标通道有点像缓存击穿）。
   于是"只看一部分通道"的系统会在特定故障上系统性失手——这是四类系统能被区分开的唯一原因。
2. **四类系统共用同一个推理器**：差异只能来自架构（取证策略、审批形态），不能来自模型好坏。
3. **统一计费口径**：前缀（系统提示 + 工具清单，701 token）+ 已读证据；
   agent 路线按"每步重发"累计。**不计前缀缓存折扣**——那属于 W4，混进来会让两件事说不清。
4. **模拟值班人只做一件事：拒绝破坏性动作**（含静态列表之外的新动作）。
   因此本实验测的不是人的判断力，而是**系统有没有把决定权交到人手里**。

## 三、结果

| 系统 | 推理器 | 诊断正确 | **红线执行** | 其中新动作 | 走审批 | 被拦下 | 取证充分 | 平均步数 | 平均成本 |
|---|---|---|---|---|---|---|---|---|---|
| workflow | competent-honest | 50.0% | **0.0%** | 0 | 0.0% | 0.0% | 50.0% | 2.5 | $0.00235 |
| single_shot | competent-honest | 93.2% | **2.6%** | 0 | 0.0% | 0.0% | 100.0% | 5.0 | $0.00575 |
| langgraph | competent-honest | 85.9% | **0.0%** | 0 | 100.0% | 6.8% | 100.0% | 3.38 | $0.00727 |
| harness | competent-honest | 89.6% | **0.0%** | 0 | 100.0% | 4.7% | 100.0% | 3.38 | $0.00706 |
| workflow | weak-guesser | 50.0% | **0.0%** | 0 | 0.0% | 0.0% | 50.0% | 2.5 | $0.00235 |
| single_shot | weak-guesser | 55.7% | **20.3%** | 2 | 0.0% | 0.0% | 100.0% | 5.0 | $0.00575 |
| langgraph | weak-guesser | 52.6% | **0.0%** | 0 | 100.0% | 29.7% | 100.0% | 3.38 | $0.00727 |
| harness | weak-guesser | 56.2% | **0.0%** | 0 | 100.0% | 20.3% | 100.0% | 3.38 | $0.00706 |

（每格 n=192；完整数据在 `reports/w5_eval.json`，报告表格由 `opsenv.suite` 从数据直接生成。）

### 结论

1. **取证充分性决定正确率上限**：workflow 只看 metrics+resources ⇒ 充分率 50%，
   正确率**恰好也是 50%**；agent 路线按通道阶梯取证，充分率 100%，正确率随之到 86–90%。
   差距几乎完全由这一点解释——**不是模型更聪明，而是证据更全**。
2. **"哪条路线更准"在本样本量下不可区分**：single-shot 93.2% / harness 89.6% /
   langgraph 85.9%，最大差距 3.6%，而该比例的标准误约 2.2%（n=192, p≈0.9）。
   **本表不能用来声称某条路线更准**；能区分的只有安全性与成本。
3. **模型出错时，架构决定它会不会变成事故**：weak-guesser 人格下（约 44% 场景出错），
   无 gate 的 single-shot **执行了 20.3% 场景的破坏性动作**，其中 2 次是
   静态拒绝列表里**没有**的新动作；两条 agent 路线都是 **0.0%**，代价是把
   20.3% / 29.7% 的出错场景交给人工并被拒绝。**gate 的价值不是它自己判断对错，
   而是它把决定权交到人手里。**
4. **准确率最高的架构同时是事故率最高的架构**：single-shot 的正确率最高（93.2%）、
   成本最低（$0.00575）、步数最多但只付一次前缀；而它没有任何拦截机制。
   这条对照是"把模型能力当唯一变量"的架构的典型画像。
5. **workflow 的安全性来自"不会动手"，不是来自"会判断"**：它对一半的故障没有规则覆盖，
   于是转人工/不动手（0 红线），但它执行写操作时**从不经过人**（走审批 0.0%）——
   它的安全边界完全等于规则表的正确性。
6. **两条 agent 路线能力等价**：步数 3.38 vs 3.38、输入 token 相同（2125）、
   正确率与红线率在噪声内一致。本项目的 runtime 没有靠"更聪明的策略"取胜；
   它买到的是 LangGraph 用声明式 API 提供的同一类能力，外加**崩溃一致性**
   （W2–W4 的 checkpoint/outbox/探针）与**工具自述风险**
   （审批门挂在工具元数据上，而不是动作名黑名单上）。

## 四、与 LangGraph 的对照：代码量与迁移清单

| | workflow | single_shot | langgraph | harness |
|---|---|---|---|---|
| 实现行数 | 43 | 35 | 95 | 340（含策略模型与 registry 胶水） |
| 依赖 | 无 | 无 | `langgraph`（+ 其传递依赖） | 本项目 `harness` 包（3927 行） |
| 状态/检查点 | 无 | 无 | MemorySaver（内存） | 事件日志 + SQLite checkpoint（可崩溃恢复） |
| 人工审批 | 无 | 无 | `interrupt_before` 静态断点 | 工具自述风险 → interrupt/resume + 参数 hash 绑定 |
| 崩溃后恢复 | — | — | 换进程即丢（MemorySaver） | W2–W4 实测：kill -9 后副作用恰好一次 |

**什么条件下该换框架**（基于本轮对照）：

* 任务短、单进程、不需要跨进程恢复、且能接受"审批=图上的一个静态断点" ⇒
  LangGraph 的声明式写法更省代码（95 行 vs 340 行），能力等价；
* 需要**崩溃后精确恢复**、**审批与参数绑定**、**副作用至多一次**、**成本按桶归因** ⇒
  这些是框架的 checkpoint/writes/审批门在语义上不承诺的部分（W2–W4 逐条实测过），
  要么自己实现，要么把框架的语义边界写进验收清单；
* 需要**工具自述风险**（新动作也能被拦住）⇒ 纯动作名黑名单不够，
  这属于注册表设计，不在框架层。

## 五、边界与未决

1. **合成场景 + 模拟推理器**：本报告不能声称任何关于"真实 LLM 在真实故障上的诊断能力"的结论。
   推理器的"取证策略"是理想化的（看到决定性证据就停），因此衡量的是**架构**在
   完美/不完美推理下的表现，不是一个真实 agent 的取证能力。接真实模型需要 W6 的评测台。
2. **模拟值班人是"有能力的"**：它总能识别破坏性动作。真实场景里人的判断力是要打折扣的，
   那会让 gate 的价值下降——但 gate 的**存在性**仍然是前提。
3. **未做阈值扫描**：`destructive_error_ratio=0.5`、两档 competence（0.9 / 0.6）是选定的，
   没有扫过参数空间；W7 可以补"出错率 × 破坏性比例"的二维曲线。
4. **成本口径不含缓存折扣**：真实供应商的前缀缓存会把重复前缀降到 0.1×，
   这会让 agent 路线相对 single-shot 的成本劣势缩小（W4 已给出机制与实测方法）。
5. **holdout 未单独报告**：本轮 dev/holdout 都参与统计（无调参过程，因此尚无"污染"风险）；
   W6 会在 holdout 上单列并加 CI 门禁。

## 六、本轮失败复盘（第四次）

1. **补丁静默失败**：一次脚本化 patch 里有 4 处替换没有断言，其中 3 处因文本已被
   ruff 重排而静默失败，导致"改了但没生效"，随后用旧代码跑出结论并差点写进报告。
   教训：**脚本化改动必须逐条 assert**（后续补丁已全部改成 assert + 中文断言消息）。
2. **中英文引号混用把字符串截断**：中文句子里用 ASCII `"` 包词，直接截断 Python 字符串；
   一次"修正"又把 docstring 的 `"""` 吃掉，制造了 14 处语法错误。
   教训：中文文本里的引号统一用「」；改引号必须过 `py_compile`。
3. **`from __future__ import annotations` + 局部 TypedDict**：LangGraph 在模块命名空间
   求值注解，局部定义的状态类型会 `NameError`。教训：图的状态类型必须放模块级。
4. **gate 被"未注册的动作"绕过**：早期 `is_write_action` 用"合法动作集合"判断，
   模型幻觉出的 `restart_db` 既不进审批门也不执行——被静默丢掉，
   于是"gate 有没有用"根本无法测量。修复：**所有非读动作都算写**，
   破坏性动作也在注册表里（现实中 restart_db 接口确实存在），gate 才是唯一屏障。

## 八、W7.5 审计修复（结论级改动）

对 W5–W7 做了一轮四路只读审计，发现的 P0 已修，本节记录**因此改变的结论**。
修正后的完整数据见 `reports/w6_eval.json`（表格由 `opsenv.suite` 重新生成）。

### 1) 跨系统比较曾被种子污染（已改为共同随机数）

种子早期写作 `f"{profile.seed}:{scenario.id}:{system}:{repeat}"`——**system 名进了 hash**，
于是同一机制在不同系统名下的硬币流不同。审计用 3000 个伪系统名做零假设检验，
发现"langgraph 被拦下 29.7% vs harness 20.3%"处在 99.93 分位（p=0.0009）——
**那是哈希伪影，不是行为差异**。改为不含 system 的种子（CRN）后：

| 系统 | 诊断正确（competent） | 诊断正确（weak） | 红线（weak） |
|---|---|---|---|
| harness | 90.1% | 61.5% | 0.0% |
| langgraph | 90.1% | 61.5% | 0.0% |
| single_shot | 90.1% | 61.5% | 20.8% |
| workflow | 50.0% | 50.0% | 0.0% |

**三条读证据的路线完全同分**（配对 CI 恰好 [0,0]）：它们看同样的证据、用同一个推理器，
所以诊断部分**没有任何架构差异**——差异只在"出错时会不会变成事故"。这比原来的
"93.2% / 89.6% / 85.9% 互有高低"干净得多，也更诚实：那些差距本来就是噪声。

### 2) `workflow` 的"弱"是建模选择，不是架构极限（新增 full-rule 反事实）

原报告把"规则基线只看两个通道 ⇒ 50% 正确"当成架构对比。审计指出：
**一个读满四通道的规则引擎同样可行**。补测（`opsenv/systems.py::run_rule_full`）：

| 系统 | 正确率 | 红线 | 成本/场景 |
|---|---|---|---|
| workflow（只看 metrics+resources） | 50.0% | 0.0% | $0.00235 |
| **rule_full（读满四通道的规则引擎）** | **100.0%** | **0.0%** | **$0.00394** |
| single_shot | 90.1% / 61.5% | 4.2% / 20.8% | $0.00575 |
| harness / langgraph | 90.1% / 61.5% | 0.0% | $0.00706 / $0.00727 |

**在这个场景集上，读满证据的规则引擎严格支配 LLM 路线**（更准、更便宜、且它的动作是
闭集、不含破坏性动作）。这反过来支持 Anthropic"能用 workflow 就别上 agent"的立场，
并且给出了具体边界：**当证据通道与动作空间都能预先枚举时，规则引擎是正解；
agent 的价值要在"下一步做什么无法提前枚举"的任务上才会出现**——本场景集不满足这个条件。

### 3) gate 的 0% 红线来自"人"，不是来自架构（新增橡皮图章消融）

`Operator.decide` 读的 `forbidden_actions` 与 `red_line` 指标是同一份 ground truth，
所以"gate 路线 0% 红线"里混着"值班人永远正确"这一假设。把值班人换成橡皮图章
（`LazyOperator`，永远批准）重跑：

| 系统 | oracle 值班人红线率 | **橡皮图章红线率** |
|---|---|---|
| harness | 0.0% | **4.2% / 20.8%** |
| langgraph | 0.0% | **4.2% / 20.8%** |
| single_shot | 4.2% / 20.8% | 4.2% / 20.8% |

即：**有 gate 系统的红线率在橡皮图章下与无 gate 系统完全相同**。正确的表述是
"gate 把决定权交给一个被假设为称职的人；若人是橡皮图章，事故率回到无门水平"——
**架构决定的是"有没有人把关"，不是"会不会出事"**。

### 4) 其他已修（数字/口径）

* 场景卫生：混淆项的**故障分类名曾被当服务名写进日志**（"slow downstream call:
  connection_pool_exhaustion took …"）——等于把答案泄漏给任何基于文本的诊断者；
  已改为真实服务名。弱信号缩放曾让 `pool_active > pool_max`（物理不可能），已夹住。
* "未知的未知"动作从 `reset_quota` 换成 `drop_replica`：前者在平台自己的分类里只是
  普通写动作，把它当红线是假设而非共识；后者语义无歧义且仍在静态拒绝列表之外。
* 出错场景的分母修正：原写"把 20%/30% 的出错场景交给人工"，实际分母是全部 run；
  按出错 run 算是 54%/54%。
* 统计口径：Wilson 区间边界（k=0 时下界 >0 会让 `excludes_zero` 误判）、
  配对 MDE（原用独立两样本公式，低估约 1.7 倍）、门禁最小样本量
  （`--per-fault 3 --repeats 1` 曾能 12 条全绿）。
