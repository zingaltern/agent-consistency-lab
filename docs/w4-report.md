# W4 实验报告：上下文工程（视图 / 卸载 / 压缩 / 缓存纪律 / 预算）

**日期**：2026-09-16 ｜ **代码**：`harness/context.py`、`cache.py`、`compaction.py`、`artifacts.py`、
`budget.py`、`llm.py` ｜ **数据**：`reports/w4_context_cost.json`、`reports/w4_crash_matrix.json`

> **边界（先说）**：本轮所有成本数字都来自本项目的**缓存模型**（前缀匹配 + 5 分钟 TTL +
> 1.25× 写溢价 + 0.1× 读折扣，最小可缓存 1024 token）与**脚本模型**（确定性、无网络），
> 不是真实 API 的实测；token 量用项目内的确定性估算器。结论是"在同一模型下的相对比较"，
> 绝对金额与真实账单不可直接对照。真实接入时替换 tokenizer / 价格表 / 缓存参数即可复用全部实验代码。

## 一、模型的三个承诺（都可测）

| 承诺 | 落点 | 断言方式 |
|---|---|---|
| 视图结构合法：工具调用与结果配对、批次原子、观测唯一 | `context.py` 的三条不变式 | 违规批次整体丢弃并记录 `View.violations`（测试 4 例） |
| 卸载确定性：同一结果两次渲染逐字相同 | 内容寻址 artifact（sha256） | `test_large_tool_result_is_offloaded_deterministically` |
| 压缩原子：要么完整生效要么完全没发生 | 先写 artifact、再追加事件 | 窗口 5 崩溃矩阵 + artifact 引用完整性断言 |

## 二、成本实验（同一条长任务：8 轮取证 + 1 次高危写 + 终答，共 10 次模型调用）

| 配置 | 状态 | token/调用 | 命中率 | 成本/调用 | 压缩次数 | 溢出 |
|---|---|---|---|---|---|---|
| E1a 纪律：动态信息在尾部 | completed | 1465 | 57.5% | $0.00288 | 0 | 0 |
| E1b 反面：动态信息进前缀 | completed | 1453 | **0.0%** | $0.00591 | 0 | 0 |
| E2a 大结果内联 + 小窗口 + 无压缩 | **failed** | 4330 | 59.3% | $0.00753 | 0 | **1** |
| E2b 大结果内联 + 小窗口 + 有压缩 | completed | 3767 | 6.7% | $0.01197 | 7 | 0 |
| E2c 结果卸载 + 小窗口 + 无压缩 | completed | **1465** | 57.5% | **$0.00288** | 0 | 0 |

### 结论

1. **缓存纪律值 2 倍成本**：把每步变化的运行时信息塞进系统提示（前缀），命中率从 57.5%
   掉到 0%，成本/调用 $0.00288 → $0.00591（**+105%**）。原因不是"少读了缓存"，
   而是每个块都要按 1.25× 重新写入：缓存写的 token 从 1969 涨到 12444。
2. **卸载是本次唯一"纯赚"的杠杆**：同一窗口下，不卸载无法在 8 轮取证内跑完（第 5 次调用溢出，
   任务 `failed`）；卸载后 token/调用从 4330 降到 1465（**-66%**），成本/调用降到
   $0.00288（**-62%**），且完全不依赖模型调用——它只是在渲染层把大结果换成摘要 + digest。
3. **压缩是拿钱买可用性**：同样内联、同样小窗口，开压缩后任务能跑完（7 次压缩、0 溢出），
   token/调用降到 3767，但**成本/调用反而是三者中最高的 $0.01197**（比卸载路径贵 4.2 倍），
   命中率只有 6.7%——每次压缩都会改写历史块序列，前缀缓存从压缩点起全部失效。
   这正是评审预判的"压缩与缓存互相冲突"，现在有了数字。
4. 因此触发策略应当是"先卸载、后压缩，压缩阈值尽量高"：本任务里卸载已经足够，
   压缩只在结果无法卸载（例如必须留在上下文里的推理链）时才需要。

## 三、崩溃矩阵（16 格 × 5 次 = 80 次运行，全部 as-predicted）

在 W3 的 14 格基础上新增两格，回答"压缩过程中崩溃会怎样"：

| 格 | 次数 | 崩溃注入 | 日志一致 | 效果数 | 压缩 | 判定 |
|---|---|---|---|---|---|---|
| during_compaction（压缩中 SIGKILL） | 5 | 5/5 | 5/5 | 1 | 7 | as-predicted |
| (long-baseline) 不注入崩溃 | 5 | 5/5 | 5/5 | 1 | 7 | as-predicted |

新增断言（`analyze()` 的 `_compaction_findings`）：

* **引用完整性**：每条 compaction 事件的 `artifact_ref.digest` 必须能在磁盘上读到
  （先写后引用，崩溃不会留下悬空引用）；
* **不重复替换**：所有 compaction 的 `replaces_event_ids` 并集里没有重复 id
  （同一批事件不会被压缩两次）；
* **任务结果不变**：压缩中崩溃 + 恢复后，副作用仍然恰好一次、日志不重不漏。

压缩的确定性 id（`compaction_id = sha256(被替换事件集合)`）让"崩溃后重算"可被检测：
重算会得到同一 id，若事件已存在则跳过，不会产生第二次压缩。

## 四、本轮新增/修改的机制

* `ViewBuilder`：纯函数式渲染（`events × 动态快照 → View`），四段布局
  `prefix / history / summary / tail`；动态信息默认进 `tail`，`dynamic_at_head` 只作反面对照。
* `PrefixCacheModel`：前缀匹配 + TTL + 最小可缓存长度 + 按模型隔离的 cache key，
  输出 读/写/普通 三类 token。
* `Compactor`：按 turn group 选择替换对象（首组与最近 K 组保留），摘要追加为
  `compaction` artifact 事件；摘要调用记 `bucket=compaction` 的账。
* `ArtifactStore`：内容寻址 + 原子替换 + `read_artifact` 工具（按切片读回，progressive disclosure）。
* `BudgetLedger`：分桶（main / compaction / judge / tools）、事件持久化、dispatch 前硬停 +
  响应后复核；预算超限产生 `fatal` 错误事件并把任务判失败。
* `LLMClient`：唯一模型出口——窗口检查（`input + max_output > limit` ⇒ `ContextOverflow`，
  由 loop 决定压缩重试或失败）、缓存计费、预算记账三件事收在一处。

## 五、失败复盘（第三次）

**风险点**：为了让 E2a 溢出，我把日志行文本缩短了一点点（去掉半句提示语），
结果单次结果从 1900 token 降到 1300，E2a 从 `failed` 变成 `completed`——
**实验结论被一行无关紧要的文案改动推翻了**。
**处理**：把长场景的日志量固定为 60 行（而不是 40 行）并在报告里写明"溢出与否对内容体量敏感"，
同时在实验脚本里保留完整配置（`--window-tokens` / `--max-inline-tokens`），使任何结论都能被复算。
**教训**：涉及阈值（窗口、缓存、截断）的实验，必须把"输入体量"当成实验变量写进报告，
否则一次文案改写就能让"结论"翻面。

## 六、边界与未决

* 掉电语义、多进程并发仍未覆盖（沿用 W2/W3 的边界）。
* `judge` 桶已定义但尚无判分调用（W6 接入评测时启用）。
* 压缩只做"摘要 + 丢弃"，没有做"分层摘要"（多次压缩的摘要再摘要）；
  当前实现里每次压缩独立，长期运行会产生多条并列摘要。
* 微压缩（按时间清理旧工具结果）目前等价于"渲染时卸载"，没有做"卸载后再回收"
  的 GC 策略；`ArtifactStore.orphan_count` 只是把孤儿暴露出来，未实现回收。
